# 2.5b — snelheid

> **Regel van dit onderdeel (besluit G25): eerst meten, dan pas optimaliseren.** Alles hieronder
> heeft een gemeten cijfer vóór én ná. Waar dat cijfer zegt "hier is niets aan de hand", staat dat
> er ook — dat is een geldige uitkomst en de reden dat er van de kandidatenlijst dingen *niet*
> gerepareerd zijn.

**Gemeten tegen:** de echte productiedatabase (Neon, PostgreSQL 17.10, `neondb`) — 211.317
producten, 210.121 prijzen, 438 merken, 438 prijslijsten, 204 spec-regels, 1.481 events.
**Datum:** 3 augustus 2026. **Basis:** `origin/main` = `6f0a47b`.

---

## 0. Hoe er gemeten is (en waarom de getallen zo betrouwbaar zijn als ze zijn)

**De queries komen uit de code, niet uit mijn hoofd.** Elke gemeten query is opgevangen met een
`drizzle-orm/pg-proxy`-client die de SQL vastlegt en 0 rijen teruggeeft. Er is dus geen enkele
plek waar ik "ongeveer wat de app doet" heb nagetypt; de gemeten tekst ís de tekst die de
repo-functie genereert, bindparameters en al. Dat bleek meteen nodig ook — zie §5.

**Alle cijfers zijn `Execution Time` uit `EXPLAIN (ANALYZE, BUFFERS)`, serverzijdig**, elke query
3–5× warm gedraaid. Wandkloktijd vanaf deze werkplek is nutteloos als maatstaf: de round-trip naar
`us-east-1` is hier **114 ms** (gemeten met `select 1`, 6×), terwijl Vercel in dezelfde regio
draait. Waar het aantal round-trips ertoe doet (serieel vs. `Promise.all`) staat dat er expliciet
bij; verder zijn de getallen puur databasetijd.

**Schrijvende experimenten zijn op de Neon-branch `enrichment-serien` gedaan**, niet op productie.
Die branch is een kopie met identieke rijaantallen (211.317 / 210.121). Metingen zijn er dus
paarsgewijs: vóór en ná op dezelfde database. De absolute cijfers van branch en productie lopen
soms uiteen (koudere cache, andere autovacuum-stand — de fuzzy-query meet 101 ms op productie en
230 ms op de branch); de *verhoudingen* zijn consistent, en waar een verandering geen schema nodig
had is er gewoon op productie gemeten.

### 1a/1b — de exacte SKU-tak was de grootste vondst, en stond niet op de lijst

De matcher doet vóór alles een exacte match op artikelnummer. `lib/matching/engine.ts:426`:

```sql
regexp_replace(lower(article_code), '[^a-z0-9]', '', 'g') = $1
   or regexp_replace(lower(supplier_article_code), '[^a-z0-9]', '', 'g') = $1
```

`products_article_code_idx` staat op de **kale** kolom en kan een uitdrukking daarover niet
bedienen — precies de klasse van B5, maar op een veel hetere plek: deze query draait **één keer
per spec-regel** in `runMatcher`.

```
vóór:  Parallel Seq Scan on products   276 ms
ná:    BitmapOr → Bitmap Index Scan on products_article_code_key_idx
                → Bitmap Index Scan on products_supplier_article_code_key_idx
                                        0,10 ms
```

Gemeten met een artikelnummer dat écht bestaat (`L028F1077009`) én met één dat niet bestaat; beide
0,1 ms. Bij een armaturenboek van 200 regels is dat **55 s databasetijd → 0,02 s**. Dat is een
grotere winst dan alles op de kandidatenlijst bij elkaar.

`lib/repo/products.ts:94` doet hetzelfde met een ándere normalisatie (`lower(x) = lower($1)`,
zonder streepjes weg te halen) en had daarom een eigen index nodig: 55 → 0,11 ms. Dat de twee
zoekpaden verschillend normaliseren is bestaand gedrag; ik heb het niet gelijkgetrokken (dat is
een gedragswijziging, geen snelheidsingreep) — wel staat het in `HANDOVER.md`.

### 1c — B5: de bevinding klopt, de opgegeven factor niet

De reviewzwerm noteerde bij B5 "153 ms vs 0,8 ms, factor ~190". **Die factor is niet
reproduceerbaar op de query die de app werkelijk stelt**, en dat is geen muggenzifterij: het
verandert wat de reparatie waard is.

De volledige query (`limit 40`, mét de `ORDER BY` die de code meegeeft) op productie:

| merk | rijen die matchen | huidige conditie | met gewone `ilike` (dus indexeerbaar) |
|---|---|---|---|
| Prado | 7.321 | 185 ms | 63 ms |
| XAL | 31.420 | 345 ms | 230 ms |
| Lombardo | 65.096 | 660 ms | 310 ms |

De 0,8 ms uit de zwerm hoort bij een merk met weinig producten en/of zonder de sorteerstap. In het
echte plan is de seq scan **niet** de hoofdmoot: de `ORDER BY similarity(name, $q) DESC, name ASC`
sorteert álle matchende rijen vóór de `LIMIT 40`, en die sortering blijft staan, index of niet.

```
vóór (XAL):  Parallel Seq Scan on products  312 ms   →  Sort 3× ~334 ms  →  345 ms totaal
ná   (XAL):  Bitmap Index Scan on products_brand_key_trgm_idx
             + Parallel Bitmap Heap Scan            →  Sort            →  228 ms totaal
```

De reparatie is dus **een halvering, geen factor 190**. Nog steeds de moeite waard, en de
resterende tijd zit in de sortering — daar kom ik in §3 op terug.

**Keuze: expressie-index, geen gegenereerde `brand_key`-kolom.** Beide lossen het op. Doorslag:

- **Deployvolgorde.** Elke push naar main deployt binnen ~3 s en er is geen aparte migratiestap,
  dus de nieuwe code draait even tegen het oude schema. Een index toevoegen is in die volgorde
  altijd veilig; een kolom waar de code meteen op leunt niet.
- **Eén waarheid.** De conditie in de code blijft letterlijk staan. Bij een gegenereerde kolom
  bestaat de normalisatie twee keer (in de kolomdefinitie en in `brandKeyOf`) en kunnen die uit de
  pas lopen zonder dat iets rood wordt.
- **Kosten.** De zes indexen samen zijn 37 MB naast een tabel van 44 MB; bouwen duurde 3,7 s op
  211k rijen (gemeten op de branch met de migratiebestanden zoals ze in de repo staan).

Nagemeten dat de index óók met een **bindparameter** wordt gebruikt (de app stuurt `like $2`, geen
literal) — ja. Voetnoot: bij een sessie-`PREPARE` schakelt Postgres na 5 executies naar een generic
plan en dát plan is trager (574 ms). Niet van toepassing hier: de Neon-HTTP-driver stuurt elke
query los, er zijn geen sessie-brede prepared statements.

### 2 — compleetheid merkrelaties: de begrenzing werkt, de join eronder niet

`getAllBrandCompleteness` is sinds de UX-audit begrensd tot de zichtbare pagina
(`app/data/brand-relations/page.tsx:66`). **Die begrenzing doet precies wat ze belooft:**

| variant | tijd |
|---|---|
| onbegrensd (alle 438 merken, zoals vóór de UX-audit) | **1.050–1.180 ms** |
| begrensd, pagina 1 (25 merken, 1.000 producten) | **22 ms** |
| begrensd, zwaarste pagina (25 merken, 65.850 producten — met Lombardo erin) | **318 ms** |

Op pagina 1 is dit dus **geen bevinding**, precies zoals de opdracht voorzag. Op de zwaarste
pagina wel, en het plan wees exact aan waarom — niet de 66 `count(*) filter`-uitdrukkingen
(samen 65 ms), maar de gecorreleerde prijs-`EXISTS`:

```
Bitmap Heap Scan on products (65.850 rijen)     12 ms      1.780 buffers
SubPlan 1  (65.850 loops)                      ~305 ms   526.801 buffers
  └ Index Only Scan on price_lists_pkey                  Heap Fetches: 65850
```

Die `join price_lists` leverde niets meer op. Sinds 1.6-A wordt er niets uit gelezen en niet op
gefilterd, en hij kón geen rij wegnemen: `prices.price_list_id` is `NOT NULL` met een
**gevalideerde** foreign key naar de primary key van `price_lists`, dus elke prijsrij heeft per
constructie exact één lijst. Weg ermee:

```
vóór  318 ms   528.581 buffers
ná    209 ms   265.181 buffers      (pagina 1: 22 → 16 ms)
```

De aanname die dit licenseert is een schema-eigenschap, geen query-eigenschap. Ze staat daarom nu
als test (`lib/repo/brand-relations.test.ts`): wordt `price_list_id` ooit nullable of verdwijnt de
FK, dan verandert het cijfer stil en gaat de test rood.

**Wat ik hier bewust níét heb gedaan:** de resterende ~200 ms zit nog steeds in 65.850
gecorreleerde probes. Losgetrokken naar een aparte, parallelle query haalt die 140 ms — 65 ms voor
de 65 kolom-aggregaten, 140 ms voor de prijs-semijoin, gelijktijdig. Dat is ~70 ms winst op één
pagina, tegen een herstructurering van `completenessSelection` (twee queries samenvoegen in JS)
die de "beide codepaden geven per definitie identieke cijfers"-garantie uit die functie zou
verzwakken. Niet gedaan; de meting staat hier voor als iemand het later toch wil.

### 3 — `listPriceListStatus`: 18 MB sorteren om 438 rijen te tellen

`LEFT JOIN prices` + `GROUP BY` over de prijslijst-kolommen betekent dat alle 210.121 prijsrijen
door de join gaan en gesorteerd moeten worden om te kunnen groeperen. Postgres schatte 189.224
groepen (het zijn er 438), koos daarom `GroupAggregate`, en die viel op schijf:

```
Sort  Sort Method: external merge  Disk: 18256kB     temp read=2282 written=2288
GroupAggregate  rows=189224 (geschat) / 438 (werkelijk)
Execution Time: 220 ms
```

Tellen vóór de join — een subquery die zelf per `price_list_id` groepeert (438 rijen,
`HashAggregate`) en pas daarna aangekoppeld wordt — maakt er **51 ms** van. Geen schemawijziging.

De uitkomst is per definitie gelijk (`count(prices.id)` over een LEFT JOIN = het aantal niet-NULL
prijsrijen per lijst; `coalesce(…, 0)` waar de join een NULL-rij gaf), en de test draait de oude
formulering ernaast op dezelfde data met vier lijsten die 0, 1, 1 en 3 prijzen dragen.

### 4 — `/analytics`: negen tegels van niks en één van 103 ms

Alle tien tegels draaien in één `Promise.all`, dus de traagste bepaalt de pagina. Serverzijdig,
per tegel:

```
0 period                 1,2 ms      5 searchTerms            0,4 ms
1 consideredProducts     5,0 ms      6 brandsNotInCatalogue  112,0 ms   ← de pagina
2 statusMix              0,4 ms      7 brandLoadQueue         0,09 ms
3 breakdown              0,4 ms      8 unmetSpecs             0,4 ms
4 gaps                   0,1 ms      9 projects               0,2 ms
```

Tegel 7 toetst 186 spec-regels met `NOT EXISTS` tegen 211k producten. Zonder index bouwt Postgres
een hash anti-join over de héle productentabel — `Batches: 8 (originally 2)`, spillend naar temp —
om er 186 rijen tegen te houden. Met een expressie-index op `lower(btrim(brand_name))` worden het
186 index-probes: **103 → 0,54 ms**.

### Waarom een expressie-index een eigen test kreeg

Een expressie-index faalt **stil**. Postgres matcht hem structureel tegen de uitdrukking in de
query: één spatie verschil, een andere quote-vorm, en de index wordt genegeerd — geen fout, geen
waarschuwing, alleen weer een seq scan. Een test die `pg_indexes` afvinkt zou dan groen blijven
terwijl de hele winst weg is.

`db/migration-0017.test.ts` doet daarom drie dingen op een echte Postgres (PGlite, met exact de
productie-migraties): (1) Postgres de uitdrukking uit de code laten plannen en op de indexnaam
toetsen (`enable_seqscan = off`, want op drie testrijen kiest hij altijd een seq scan); (2) de
uitdrukking uit de bronbestanden zelf lezen en tegen de migratie leggen, met een regex die
alléén de kolomplek vrijlaat — geverifieerd dat die rood wordt op een verschil van één spatie;
(3) bewijzen dat dezelfde zoekopdracht mét en zonder de indexen identiek dezelfde rijen in
dezelfde volgorde geeft.

### `/catalog`'s merken-keuzelijst (B4) — de fix leverde geen meetbare winst op

Dit hoort in dit hoofdstuk thuis omdat het precies laat zien waarom G25 "eerst meten" voorschrijft.
B4 verving `selectDistinct(brandName).from(visibleProducts)` (gemeten: 262 ms) door de semi-join in
`lib/repo/catalog.ts`. Nagemeten op productie, beide vormen naast elkaar:

| vorm | tijd |
|---|---|
| oud: `select distinct brand_name from visible_products` | 235–248 ms |
| nu: `select distinct brand_name from products where exists (…)` | 246–275 ms |

**De nieuwe query is niet sneller; eerder een fractie trager.** De reden staat in het plan: beide
scannen `products` volledig (`Parallel Seq Scan`, 3× 70.439 rijen) en beide moeten er 210k
prijsrijen tegenaan hashen. De semi-join bespaart de kolomprojectie van de view, niet de scan.

Ik heb drie routes naar sneller gemeten en alle drie afgewezen:

| poging | tijd |
|---|---|
| btree-index op `products(brand_name)` erbij | 245–263 ms (geen verschil) |
| `recursive` loose index scan over de 32 merknamen + `EXISTS` per merk | 218–227 ms |
| merknamenlijst vooraf + `EXISTS` per merk | 146–154 ms, maar wisselvallig (480 ms koud) |

De kern: er zijn maar **32 distinct `brand_name`-waarden** onder 211k producten, en om te weten
welke 30 daarvan een geldige prijs hebben moet je hoe dan ook de prijsrijen aanraken. De enige
structurele route is een gematerialiseerde vorm of een cache — en de code wijst caching hier
expliciet af omdat ijzeren regel 3 geen TTL verdraagt (een merk waarvan de prijslijst zojuist
verliep zou N seconden in de lijst blijven staan). Die afweging deel ik. **Niets aangeraakt**; de
250 ms staat als openstaand punt in `HANDOVER.md`.

## 3. Gemeten, wél traag, bewust niet aangeraakt

**De sortering in de merk-alleen-tak.** Wat na de index-reparatie overblijft (228 ms voor XAL,
307 ms voor Lombardo) is de `ORDER BY similarity(name, $q) DESC, name ASC` over álle matchende
rijen. Bij een lege zoektekst is `similarity(name, '')` voor élke rij 0 — de sorteersleutel is
aantoonbaar constant en doet niets. Hem weglaten als de zoektekst leeg is zou de sortering
vereenvoudigen. **Niet gedaan**: dit is rangschikkingscode (ijzeren regel 2 woont hier), de
opbrengst is ongemeten zolang de tak überhaupt niet draait (§5), en het hoort bij een
rangschikkings-opdracht, niet bij een snelheidsopdracht.

**`app/projects/[id]/work-prep/page.tsx:61` — serieel `await` in een `for`-lus.** Per gematchte
spec-regel één `getEquivalentAlternatives`, strikt na elkaar. Gemeten op de branch: **360–680 ms
wandkloktijd per aanroep** (meerdere round-trips per aanroep). Bij een gegund dossier met 40
gematchte regels is dat 15–25 s serieel. **Vandaag geen meetbaar probleem**: er is geen enkel
dossier op `awarded`, en het zwaarste dossier heeft 3 gematchte regels. Ook niet triviaal te
parallelliseren — `getEquivalentAlternatives` schrijft een event per aanroep (regel 5), dus
`Promise.all` verandert de volgorde in het event-log. Schaalnotitie, geen ingreep.

**Drie seriële `await`s op het dossierscherm** (`app/projects/[id]/page.tsx:57,59,62`:
`getDossier`, `getSpecLines`, `getOpenOcrRun`). Onderling onafhankelijk, dus samen te voegen tot
één `Promise.all`. Winst = twee round-trips; vanaf Vercel in dezelfde regio ~4–10 ms. Onder de
meetruis van de pagina zelf. **Niet gedaan** — een wijziging zonder meetbare winst is precies wat
G25 verbiedt. Genoteerd voor als er ooit een langzamer pad bij komt.

## 4. Houdbaarheid — wat er omvalt als de data groeit

- **C6 (FK-indexen).** Zie §2. Eén migratie zodra `spec_lines` / `events` / `quotes` zes cijfers
  naderen.
- **`getStatusCounts` op `/projects`.** Eén query per dossier. Bij 12 dossiers in één `Promise.all`
  is dat niets; bij 500 dossiers zijn het 500 gelijktijdige HTTP-queries op de Neon-driver, en dán
  is de N+1 wél het probleem. Eén `group by dossier_id` over de gefilterde id's vervangt hem.
- **De merk-alleen-tak schaalt met het grootste merk, niet met de catalogus.** Lombardo alleen al
  is 65k producten; groeit de catalogus naar 3M SKU's (het cijfer uit de briefing) dan is 300 ms
  niet 300 ms gebleven. De sorteervereenvoudiging uit §3 is dan de eerste stap.
- **De prijs-`EXISTS` in de compleetheidsmeting** schaalt lineair met het aantal producten op de
  zichtbare pagina. Bij een groter merk komt de splitsing uit §1.2 alsnog in beeld.

## 5. Gevonden tijdens het meten, NIET gerepareerd: `/catalog` crasht op een merk zonder zoektekst

**Dit is geen snelheidsbevinding maar een productiebug, en hij zit precies op de tak die B5
beschrijft.** Melden met bewijs, niet repareren — buiten scope blijft buiten scope.

**Wat er misgaat.** `lib/repo/products.ts:121/144` zet de sorteertermen `matchCount` en
`prefixBonus` op de constante `sql<number>\`0\`` wanneer er geen naamtoken van ≥2 tekens is.
Drizzle rendert dat als `order by 0 desc` — en voor Postgres is een kaal getal in `ORDER BY` een
**positieverwijzing** naar de select-lijst. Positie 0 bestaat niet.

**Bewijs, tegen de echte productiedatabase** (`bun --env-file=.env.local`, `searchProducts`
rechtstreeks aangeroepen):

```
merk-alleen  : FOUT — ORDER BY position 0 is not in select list
               select … where regexp_replace(lower("brand_name"), …) like $2
               order by 0 desc, 0 desc, similarity(…) desc, "name" asc limit $4
1-tekenquery : FOUT — idem
               order by 0 desc, (case when "name" ilike $3 …) desc, …
merk+tokens  : OK, 5 rijen
```

**Wanneer raak je het.** Twee gevallen, allebei via de gewone UI van `/catalog`:
1. een merk uit de keuzelijst kiezen en het zoekveld leeg laten — dat is precies waarvoor de
   keuzelijst er staat;
2. een zoektekst waarin geen enkel token ≥2 tekens is (bijv. `X`).

**Dit is een bekende bugklasse in deze repo — één laag verderop is hij al gerepareerd.**
`lib/matching/engine.ts:437-441` beschrijft hem letterlijk ("*vóór deze poort crashte de query
zelfs: de constante-nul sorteertermen renderden als `ORDER BY 0`*") en zet er een poort voor:
`if (brand.length === 0 && productText.length === 0) return []`. Die poort helpt `products.ts`
niet, en zou daar bovendien verkeerd zijn — merk-zonder-tekst is dáár een geldige zoekopdracht.

**Gevolg voor dit onderdeel.** De merk-alleen-tak was met de echt gegenereerde SQL niet te meten.
De B5-cijfers in §1c zijn daarom gemeten op een surrogaat dat op één punt afwijkt: de twee
constante sorteertermen (`0 desc, 0 desc`) zijn weggelaten. Die sorteren per definitie niets — ze
zijn constant — dus `WHERE`, plan en sorteerkosten zijn identiek. De index-reparatie is
onafhankelijk geldig (ze raakt de `WHERE`, niet de `ORDER BY`) en helpt óók de merk+tekst-tak, die
wél draait. Maar: **zolang deze bug er is, levert de B5-reparatie op `/catalog` geen zichtbare
winst op, want de tak draait niet.**

Vermoedelijke reparatie (ter informatie, niet uitgevoerd): de constanten als `sql\`0::int\``
renderen of de sorteertermen weglaten wanneer ze constant zijn — plus een test die de merk-alleen-
tak daadwerkelijk uitvoert, want die bestaat vandaag niet (`lib/repo/rules.test.ts:37` zoekt met
merk **én** tekst).

## 6. Deployvolgorde

Alle wijzigingen zijn veilig in de "code eerst, migratie daarna"-volgorde die deze repo afdwingt:

- **0017 en 0018 voegen alleen indexen toe.** Geen kolom, geen view, geen constraint. De nieuwe
  code werkt identiek mét en zonder — alleen langzamer zonder. Er is dus geen venster waarin een
  push iets breekt.
- **De drie codewijzigingen (2, 3) vragen geen enkele schemawijziging.** Ze draaien op het huidige
  schema.
- **Bouwtijd van de indexen:** 3,7 s voor beide bestanden samen op 211k rijen (gemeten op de
  Neon-branch met de migratiebestanden zoals ze in de repo staan). `CREATE INDEX` zonder
  `CONCURRENTLY` neemt in die seconden een `SHARE`-lock op `products`: lezen kan door, schrijven
  wacht. Bewuste keuze — de migratierunner (`db/migrate.ts`) draait statements over HTTP en
  `CONCURRENTLY` mag niet in een transactieblok, en een paar seconden schrijf-wachttijd op een
  interne tool met één gebruiker is goedkoper dan die complicatie.
- **De migratie is nog niet op productie toegepast.** Zie het pushblok in `HANDOVER.md`:
  `bun run db:migrate` hoort erbij, en mag zowel vóór als ná de push.
